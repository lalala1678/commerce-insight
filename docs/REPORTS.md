# 第 6 步：经营诊断与报告

当前交付两份业务案例、第四个“经营报告”页面、只读报告接口，以及 Markdown / HTML / JSON 导出。

报告现在还会把可核查的变化转换成**结构化核查任务**：观察到的指标、最主要的品类和客户州、数值对应的 JSON 指针、待验证假设、需要检查或补充的数据，以及验证指标。页面中的证据名称可点击并跳到相应图表或表格。任务只说明“下一步查什么”，不自动断言变化原因。

- [履约与评价案例](reports/CASE_DELIVERY.md)：展示评分差、缺失、品类和地区结构，明确相关性边界。
- [普通周报样例](reports/samples/commerce-report-2018-07-23-2018-07-29.md)、[HTML](reports/samples/commerce-report-2018-07-23-2018-07-29.html)。

## 范围和比较期

报告共用顶部日期、品类、客户州。接口 `GET /api/reports` 默认与现有筛选一致为2018年7月，单次最多366天。完整自然月比较前一自然月，其他范围比较前一等长周期。任一期超出推荐覆盖，比较期、差额和拆解返回 null，不伪造前期数据。

只有周一至周日且恰好7天的范围称“经营周报”，其他范围称“经营期间报告”。页面按钮把结束日限制到推荐覆盖内，再回退到不晚于该日的最近周日及其前6天；保持品类和地区。如果没有足够覆盖仍会提示数据不足，“完整周”仅指日历边界。

所有金额为整数分，均值或算术拆解可带小数分。月总额必须同时显示日均金额，以提示月份天数不同；日均调整不能消除所有季节或星期构成差异。

## 可加总的变化贡献

- 品类按命中商品项金额统计；客户州按订单商品金额统计。每个维度包含两期所有键的并集，新增/消失项补零。
- 每个维度完整差额之和都等于商品金额总变化，不能将品类与地区两套分解相加。页面/文本只显示前若干项，完整列表在JSON。
- 订单与客单价采用对称分解：`ΔN×(A1+A0)/2 + ΔA×(N1+N0)/2`。内部使用精确分数验证两项之和等于金额变化。任一期零订单则无法定义客单价，拆解为null。
- 拆解是算术恒等式，不识别促销、价格或渠道带来的因果效果。

## 异常规则：same-weekday-mad-v1

检测的是已交付订单量。每个目标日只取此前7、14、…、56天，共8个同星期日，使用相同品类/地区筛选。

1. 目标日与8个基线日期必须在推荐观察范围内，否则状态为 insufficient。
2. 覆盖内没有命中记录按观察到的0单处理；历史中位数小于5单时不判断。
3. 中心值为8日订单数中位数，MAD为绝对偏差的中位数。
4. 阈值为 `max(3×1.4826×MAD, 0.5×历史中位数, 10单)`；实际值与中心的绝对差**严格大于**阈值才标 high/low，否则 normal。
5. 每个目标日返回基线起止日、有效日期数、中位数、阈值及状态。无提示不证明业务没有异常。

该规则为探索阈值，并未校准误报率，也不是正式统计检验。采用8周、50%和10单下限是为了有解释性且减少稀疏计数波动，不能声称这些参数最优。
基线不包含目标日或未来日，但所用“最终已交付状态”来自历史数据抽取，不能把本功能称为实时预警回测。

实际例子：2017-11-24观察到1,147单，历史同星期中位数134单、偏差阈值71.1648单，因此提示偏高。该日为何偏高需要额外活动、渠道或源系统证据，当前不自动归因。

## 履约与评价

按订单统计按期、延迟和日期不足三组，保留订单数、评价样本、缺失、均值、中位数、样本标准差、1–2分占比和1–5分分布。
为了检查结构差异，订单按命中商品金额最大的品类唯一归组（并列按品类名排序），另按客户州分层。两组评价样本都≥20才显示层内评分差；门槛仅用于展示，不是显著性检验。
订单级评分不归责某商品或卖家。品类与地区的分层是分别进行的，没有同时消除混杂、客户重复和选择偏差。

## 生成和保存

页面“经营报告”展示结果，可下载三种格式；同次展示与下载复用同一个响应快照，避免点击下载时数据已经变成另一版本。JSON包含完整贡献、全部日期判断、分层和规则。HTML转义所有动态文本，不执行源文本中的HTML。

`investigations` 最多生成两类任务：有可比周期、至少一期有订单，且商品金额、订单量或日均金额发生变化时，针对销售变化生成任务；按期与延迟组各有至少20条有效评价时，生成履约与评价任务。销售任务选择绝对金额变动最大的非零品类、客户州作为**各自维度**的线索，不能从两个边际排行推断其交集。没有足够证据时返回空数组和页面提示，不捏造任务。证据项保存数值、单位、页面锚点和报告 JSON 指针；如 `/contributions/category/0/delta_cents`，导出后可在同份 JSON 中核对。Markdown 与 HTML 也写入任务观察、证据、核查步骤及验证指标。

页面允许为每项任务填写负责人代号、进度（待核查、核查中、已写核查记录）和备注；选择“已写核查记录”前必须填写备注。这些输入只保存在当前浏览器的 `localStorage`，按数据版本、日期、品类、客户州和任务 ID 区分，不上传 API、不跨设备同步，也不代表实际核查已被平台验证。清理浏览器数据会删除本地进度。请使用“下载核查记录 JSON”保存一份包含任务证据与本地进度的文件；不要填写真实姓名、订单级个人信息或商业敏感内容。普通报告 JSON 下载保留原始分析快照，不混入浏览器备注。

浏览器存储按站点域名隔离，不按 `/commerce-insight/` 路径隔离；同域其他页面理论上可读取这些本地记录。当前静态快照虽然没有订单和客户标识，少数分层仍可能只有 1 笔订单，因此“聚合”不等于满足真实商家数据的匿名化要求。若接入非公开商家数据，必须重新设计权限与存储、最小样本抑制和发布审核，不能沿用本演示的静态导出规则。

命令行默认生成2018-07-23至07-29周报：

```bash
python -m scripts.export_report --output reports
python -m scripts.export_report --start 2017-11-20 --end 2017-11-26 --output reports/november
python -m scripts.verify_reports --api-url http://127.0.0.1:8000
```

数据库使用 DATABASE_URL；未设置则读取本地SQLite。相同日期的文件名固定，再次导出到同一路径会覆盖，多个筛选版本请指定不同输出目录。
自动生成指固定模板按查询结果填充，并非已配置定时任务或自动发送。每份报告记录期间、筛选、生成时间、数据版本、规则、来源许可与限制；事实和尚未执行的建议分开。
