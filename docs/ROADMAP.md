# 逐步实施路线图与模型选择

适用：会 Python 和 SQL、前端较弱，目标数据分析／商业分析岗位；每周 10–15 小时，约 8 周。
进度：第 0–6 步已完成；第 7 步的静态快照、页面与 Compose 配置通过本地检查，远程 Pages 和 Docker 工作流另行验收；第 8 步的简历、面试资料与三分钟演示已完成。履约及评价已随第 3–4 周范围提前接入。证据见 core/VERIFICATION.md、customers/VERIFICATION.md、reports/VERIFICATION.md、pages/VERIFICATION.md 和 portfolio/。可选预测为第 9 步，不属于八周主线的完成条件。

## 模型怎么选

以下是针对本项目的实践建议，不是官方针对电商项目的跑分结论，也不代表已经替你切换模型。

| 用途 | 默认模型与推理档位 | 何时调整 |
|---|---|---|
| 解释代码、补说明、修改文案、单个简单样式 | GPT-5.6 Terra · 轻度（low） | 修改涉及多个组件或逻辑时改中度 |
| 常规功能、SQL、ETL、接口、跨文件开发 | GPT-5.6 Sol · 中度（medium） | 明确且局部的修改可降到轻度 |
| 指标设计复核、关联重复计数、复杂错误 | GPT-6 Astra · 中度（medium） | 问题已复现且多种约束难以兼顾时用高度（high） |
| 预测验证方案、时间泄漏、复杂统计边界 | GPT-6 Astra · 高度（high） | 留到预测阶段，不用于日常页面调整 |

Sol 中度可以作为长期默认。Terra 用在边界清楚、容易验证的任务；Astra 在关键节点做深度检查。不要为了“更认真”把所有步骤都开到最高档。
模型连续两次没有解决同一个错误时，先提供完整错误、复现步骤和失败测试，再考虑升级模型；不要只重复“修复一下”。
如果当前可用额度充足，也可以固定用 Sol 中度而不频繁切换。推理档位不等于保证正确，验收仍由真实测试和手工核对决定。

官方资料核对日期：2026-09-17。Terra 定位为智能与成本平衡；Sol 面向复杂专业工作；Astra 面向困难的端到端任务。三者均有 low / medium / high 等推理设置。API 价格不等于 Codex 订阅额度消耗比例。

- [GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra)
- [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra)

## 第 0 步：先验收地基

按 README 启动后端与前端，检查页面显示合成数据、接口正常和三个预期数字。
执行测试和前端构建。阅读 backend/seed.py、sql/overview.sql、backend/metrics.py，理解数据在哪里变化。
你需要能解释：一笔订单买两件商品，为什么订单数仍然是 1？取消订单为什么不算？价格为什么用整数分？

进入下一步的条件：能亲自启动、能解释这三个问题。不是把截图存下来就算掌握。

## 第 1 步：读懂数据与业务

任务：

- 先读 data/raw 中订单、明细、客户三张表，记录字段、类型、主键、样本行和空值。
- 识别一对多关系，再读商品、卖家、支付、评价；不要把明细和支付直接相乘连接。
- 在 docs/DATA_DICTIONARY.md 写数据字典和表关系图，更新 METRICS.md。
- 固定已交付订单、商品金额不含运费、下单日归属和稳定客户身份等口径。

验收：每个指标都有可用字段、分子分母与排除条件；准确订单量来自实际读取，而非猜测“10 万+”；明确哪些需求无法支持。
模型：Sol 中度完成；对多表关系不确定时请 Astra 中度只做复核，不重写项目。

可复制任务：

> 先读 AGENTS.md 和 docs/ROADMAP.md，只完成第 1 步。检查 Olist 原始数据，交付数据字典、表关系图和指标口径。不要接入新页面、不要开始 ETL。解释每张表的粒度和可能导致重复计数的关联，并用实际行数和样例支撑判断。

## 第 2 步：可靠地导入真实数据

任务：建立与 demo_ 表独立的真实数据表；实现缺失、重复键、非法金额、孤立关系和日期检查；分别处理商品明细、支付、评价；在事务中导入。
交付：backend/etl.py、真实数据表定义、docs/DATA_AUDIT.md、相关测试。
验收：原始订单数与入库数能解释；明细金额完全核对；同一数据重跑两次结果相同；错误输入被拒绝并保留此前有效数据；记录文件版本摘要。
模型：Sol 中度；出现金额放大或跨表难以定位的问题用 Astra 中度。

> 只完成路线图第 2 步：依据已确认口径实现 Olist ETL 和 MySQL 入库。保留 demo_ 样例。先检查数据，再落库，提供重复导入、金额核对和错误输入测试。运行并报告实际数量，不开始 RFM 或页面扩展。

## 第 3 步：建立统一指标接口

任务：新增真实数据概览、日趋势和品类/地区聚合；接收明确日期范围；使用同一个筛选订单集合计算金额和客单价；添加日期边界和空集合处理。
交付：可阅读的 SQL、API 文档、接口测试和独立核对结果。
验收：随机选择至少三个筛选范围，API 与独立 SQL 金额一致；多商品不放大订单数；非法日期返回清晰错误；零订单客单价返回 null。
模型：Sol 中度。

> 只完成第 3 步，新增真实数据的核心指标接口与时间、品类、地区筛选。先定义接口和口径，然后实现并核对三个范围。不要把模拟结果混入真实接口，也不要改造整套前端。

## 第 4 步：让分析能被操作

任务：将基础页面连接真实接口；使用 ECharts 做日/周/月趋势、品类和地区排名；增加筛选；商品页展示 TOP 与低销量商品。
验收：筛选后所有相关卡片和图表同步；没有数据不显示伪造示例；错误、加载、手机宽度可用；低销量不写成库存滞销。
模型：Terra 中度做独立页面任务；涉及接口改动与联调时 Sol 中度。

> 只完成第 4 步，把已通过测试的真实数据接口接入 Vue，做经营概览和商品页。先复用组件，不添加账户和复杂权限。检查筛选、加载、错误、空数据和窄屏；禁止在接口失败时回退成看起来真实的假数据。

## 第 5 步：客户分析（已实现）

任务：用 customer_unique_id 识别客户；解释数据内首次购买；指定复购观察窗口；按历史截止日计算 RFM，先查看 F 的分布再定规则。履约及评价接口已在第 3–4 周实现，后续复用现有口径。
验收：每位纳入客户恰好属于一个客群，分群人数合计一致；样本缺日期不能混入分母；评价缺失不能当 0 分；订单评价不能直接归责给单个商品。
模型：Sol 中度实现，Astra 中度审阅指标边界。

> 只完成第 5 步。先说明新老客、复购率、RFM 和延迟率的口径及数据局限，再实现 SQL、接口和页面。不要强行五等分 RFM，不用今天计算历史 R 值。用真实结果验证分群覆盖和缺失日期分母。

## 第 6 步：形成可讲的业务案例（已实现）

任务：完成销售变化拆解、履约与评价诊断两份案例；添加只看历史同星期的异常提示；用固定模板导出周报。
每份案例包含：业务问题 → 样本与口径 → 发现 → 证据 → 建议 → 如何验证 → 限制。
验收：数值能追溯到 SQL/接口；比较期完整且明确；异常规则不使用未来数据；不存在凭空归因和虚构收益；没有明显关系就如实记录。
模型：Sol 中度实现；Astra 中度审阅结论是否超过证据。

> 只完成第 6 步，基于实际计算写两份案例并实现模板周报和历史异常规则。不接 LLM API。所有数字来自数据，建议不写成已实现收益，相关性不写成因果；若数据不支持预设结论，明确说明。

## 第 7 步：别人能看、能运行（本地实现；远程发布另验）

任务：验证 MySQL Docker 路径；把相同指标结果导出为限定范围 JSON；前端区分 API 与静态模式；创建 GitHub 仓库并配置 Pages 工作流。
验收：新环境能按文档启动；静态版只允许有数据的筛选；快照与接口数值一致；不提交原始数据和密码；页面标历史演示，不能说实时。
模型：Sol 中度。不要让 Pages 直接连接 MySQL；它只托管静态文件。

> 只完成第 7 步，验证本地 MySQL 容器运行，并实现有限范围的静态 JSON 导出和 GitHub Pages 演示。复用同一指标逻辑，核对静态/接口一致性；记录仓库和发布前提，不声称未发生的上线。

## 第 8 步：转成简历与面试材料（已实现）

任务：补 README 首页、架构图、截图、3 分钟视频；写简历项目条目；准备多表关联、指标定义、RFM、数据限制和部署取舍等问答。
验收：简历只写实际完成内容与核实数字；你能不看模型回答说明两项设计取舍、一个数据问题和一个业务发现；别人三分钟内理解项目。
模型：Terra 中度整理资料，Sol 中度检查事实一致性。语言润色不需要 Astra 高档位。

> 只完成第 8 步，依据代码、测试与真实报告整理求职展示材料。不要虚构性能提升、预测精度、营收效果或用户数量。给出 3 分钟演示顺序、简历描述和需要我自己掌握的面试问题。

## 第 9 步：完成主项目后再考虑预测

先选择有足够连续历史的品类周销量，做季节性朴素基线；滚动时间验证，特征只能用预测当时可见数据；再尝试 XGBoost；报告 MAE、WAPE、零销量处理和各窗口结果。
模型：Astra 高度设计验证边界，Sol 中度实现。比基线差也必须保留真实结论。
不在当前八周主线中预留必须实现的模型承诺。
