# 第 1 周：需求与字段可行性

状态：需求基线已确定；以下为待实现功能，不表示当前基础页面已具备它们。

## 1. 谁使用、解决什么问题

用户：电商运营负责人；项目读者：招聘数据分析／商业分析岗位的面试官。
数据视角：巴西多卖家平台的匿名历史交易样本。不是一家店的全量经营系统，不能直接代表中国电商场景。

首版围绕三个业务问题：

1. 销售变化体现在哪些订单、品类和地区？分别是订单量还是客单价变化？
2. 哪些商品成交较少、哪些履约样本出现延迟？评分与履约有什么描述性关联？
3. 客户购买频次与金额怎样分布？运营人员下一步应该核查什么、怎样验证建议？

成功标准：任一页面指标能追溯到字段与 SQL；相同筛选各页面一致；可以讲清两个案例与局限。
第一版不追求覆盖所有电商业务，不把公开数据分析建议描述为已落地经营成效。

## 2. 功能 → 真实字段 → 判断

缩写：O=orders，I=order_items，C=customers，P=products，S=sellers，Pay=order_payments，R=order_reviews。

| 功能 / 业务问题 | 所需原始字段 | 分析粒度与口径 | 可行性 / 限制 |
|---|---|---|---|
| 成交商品金额 | O.order_id/order_status/order_purchase_timestamp；I.order_id/price | 已交付订单命中明细的 price 求和，不含运费 | 可做；不用支付金额替代，不称净收入/利润 |
| 订单量 | O.order_id/order_status/order_purchase_timestamp | 满足筛选的已交付订单去重 | 可做；不是 I 的行数 |
| 平均客单价 | 上述两个指标 | 同一订单集合的金额 / 去重订单数 | 可做；空集合不可计算 |
| 日/周/月趋势 | O.order_purchase_timestamp + 金额字段 | 按下单时间分组；周从星期一开始 | 可做；边界周/月标不完整，不补造缺失业务 |
| 商品、品类 TOP / 低销量 | I.product_id/order_item_id/price；P.product_id/product_category_name | 商品项数量与商品金额；低销量只在有成交商品中排名 | 可做；没有库存，不称滞销；没有商品名称正文，展示 ID 或品类 |
| 新老客 | C.customer_id/customer_unique_id；O.customer_id/order_purchase_timestamp/order_status | 用全部可见历史识别首次已交付购买，再分当前窗口新老客 | 可做但左截断；不是注册新客 |
| 观察期内复购率 | 上述客户与订单字段 | 窗口 ≥2 单的客户 / 窗口有单客户 | 可做；不等于终身复购率，窗口要明确 |
| RFM | C.customer_unique_id；O.order_purchase_timestamp/order_status；I.price | R 截止日减最近购买日；F 去重单数；M 商品金额 | 可做；频次集中于 1，先分布后规则；不保证营销效果 |
| 用户画像/购买偏好 | C.customer_state；P.product_category_name；I.price | 只做购买行为、地区、品类偏好 | 有限支持；没有年龄、性别、职业等人口属性 |
| 地区销售 | C.customer_id/customer_state；O.customer_id；I.price | 客户州；按销售和客户数统计 | 可做；不必连接百万行地理表 |
| 交付时长与延迟率 | O.order_delivered_customer_date/order_estimated_delivery_date/order_purchase_timestamp/order_status | 一单一条；有效日期分母单独计算 | 可做；缺失与时序异常需要标记 |
| 评分与履约对比 | R.order_id/review_score/review_answer_timestamp；O 交付日期 | 先确定单订单评价规则，再按履约分组 | 可做描述性比较；缺评价不是 0；相关性不代表因果 |
| 卖家观察 | I.seller_id/order_id；S.seller_id；O 履约；R 评分 | 卖家关联订单去重并披露多卖家订单 | 有限支持；不能认定订单级坏评由该卖家造成 |
| 销售变化拆解 | 商品金额、订单量、品类、客户州 | 两个明确比较期；代数贡献，不是因果归因 | 可做；月份天数不同要披露，不能推断促销/广告原因 |
| 异常日期提示 | O.order_purchase_timestamp + 聚合订单量/金额 | 仅参考目标日前同星期数据 | 可做待核查规则；不能判定欺诈或活动效果 |
| 自动经营报告 | 前述已计算指标、筛选范围、版本号、缺失计数 | 复用同一指标层，模板生成 | 可做；先不接入 LLM，不生成无依据的原因 |
| 商品销量预测 | I.product_id + O.order_purchase_timestamp/order_status | 后续优先品类周销量，基线与滚动回测 | 仅后续实验；无库存/促销，最终状态含事后信息 |
| 退款率 | 需要退款单、退款发生时间、退款金额和原因 | 当前只有 canceled 等订单状态 | 不支持；取消不等于退款 |
| 广告 ROI/ROAS、转化率 | 需要广告支出、曝光、点击、访问、归因链 | 当前交易表没有这些信息 | 不支持；商家入驻漏斗不是消费者漏斗 |
| 利润、库存周转与零销量滞销 | 需要成本、库存快照、上架状态与经营费用 | 当前只有成交与商品属性 | 不支持；不能用售价减运费充当利润 |

## 3. 页面与开发顺序

1. 经营概览：统一日期/品类/客户州筛选，金额、订单、客单价、趋势。
2. 商品与履约：品类/商品排名、低销量、交付、评分；避免将商品行当订单。
3. 客户分析：数据内新老客、窗口复购与 RFM；同时展示窗口和样本量。
4. 经营报告：事实、变化、待核查、建议、验证方案和限制。

第 2 周只推进真实 ETL 与数据核对；没有通过金额/订单数校验前不扩展页面。
不引入账户系统、实时事件流、多租户、自动投放或库存采购建议。
