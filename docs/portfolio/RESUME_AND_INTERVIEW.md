## 常见追问与回答要点

**1. 为什么只统计已交付订单，时间却用下单日？** 这是固定的历史完成状态口径，便于观察最终完成交易对应的下单趋势。它会使用后来才知道的最终状态，因此不能称为当时实时可见的销售额。另一种口径（按支付或交付日）会回答不同问题，需要另立指标。

**2. 多表关联怎样避免金额翻倍？** 商品项是订单一对多，支付和评价也可能一对多。先把商品项与支付分别按订单汇总、评价每单确定一条，再建立订单事实；品类金额仍从商品项求和。用 5 笔手算样例覆盖多商品、多支付、多评价，再用原始 CSV 独立计算金额，与 MySQL 和 API 逐层核对。

**3. 商品金额、运费和支付额为何可能不同？** 商品金额只加 `price`，不含 `freight_value`；支付是整单支付记录，可能多次支付或缺失。选品类时只加该品类商品项，但支付仍是整单量，不能直接比较两者并叫做退款或利润。

**4. 7 月总额增长，为什么不说经营改善？** 6 月 30 天、7 月 31 天，7 月总额 +1.39%，日均反而 -1.88%。日均也未控制周几、季节与活动，因此先拆订单量、客单价、品类及地区贡献，再建议取等长且星期结构可比的周期核查。

**5. “老客”和“复购客户”有什么区别？** 老客指本窗口购买前，在可见历史里已有已交付购买；复购客户指本窗口命中订单至少两笔。一个老客本月可只买一次，一个新客本月可买两次。7 月购买客户 6,100，其中新客 5,949、老客 151，窗口复购客户 58；左截断使“新客”仅是数据内新客。

**6. RFM 为什么不用常见五分位？** 三个检查窗口的购买频次 P75 都是 1，强行按 F 五等分会拆开相同行为或产生重复边界。当前规则固定 R≤30 天、F≥2、M≥R$200 的二分，组成 8 个互斥且覆盖窗口购买客户的组。阈值是探索性的，不能当作最优客户价值模型。

**7. 评价低能否证明配送延迟导致？** 不能。7 月延迟组平均 2.755 分，按期组 4.370 分，但样本量、评价缺失与品类地区构成不同；评价与收货的时序也不保证。报告给出分层描述和核查方案，没有进行因果估计或显著性结论。

**8. 异常提示如何避免未来信息泄漏？** 每个目标日只取此前 8 周相同星期的订单数，计算中位数与 MAD，加绝对和相对阈值。基线不含当天及未来日；历史不足或稀疏时显示“数据不足”。然而样本使用最终已交付状态，不能包装成实时预警回测，阈值也未校准误报率。

**9. 为什么在线展示和本地后台不同？** GitHub Pages 只能托管静态内容，在线版使用限定筛选的预计算聚合 JSON。完整订单查询与任意合法筛选由本地 FastAPI 连接 MySQL 提供。两者复用同一指标结果，发布时应逐字段核对；静态版不应显示不可用的筛选或个人级数据。

**10. 你会怎样继续验证业务建议？** 先确认源数据日期和评价规则，再补活动、库存、价格、投诉及物流环节数据；针对某个品类和地区预先定观察期、主要指标、辅助指标及对照。当前案例只提出验证路径，没有实施经营试点，也没有营收提升证据。
