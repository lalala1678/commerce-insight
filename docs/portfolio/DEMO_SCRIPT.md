# 三分钟项目演示脚本

目标听众：数据分析／商业分析岗位面试官。录制时优先使用本地完整版本；静态 Pages 只能演示预导出范围，不能现场随意输入日期或查询订单明细。按下表操作，数字必须与当前数据版本一致；如果源数据或规则变更，先更新脚本。

| 时间 | 画面与操作 | 讲解词 |
|---|---|---|
| 0:00–0:20 | 项目首页，显示“历史数据”和 Olist 来源 | “这是我做的电商经营分析与诊断平台。它解决三个问题：销售变化来自哪里、客户和履约表现如何，以及哪些异常值得运营继续核查。数据来自 Olist 的公开历史样本，不代表实时业务。” |
| 0:20–0:45 | 经营概览，停在 2018 年 7 月；指向四张指标卡与趋势 | “我先定义已交付订单、下单日和不含运费的商品金额，再算订单与客单价。7 月是 6,159 单、R$ 867,953.46。全量导入则是 99,441 笔原始订单，已交付 96,478 笔。” |
| 0:45–1:05 | 本地版选“床上与卫浴”及 SP、应用筛选；或切换已导出同范围 | “品类按命中商品项计金额，订单只去重一次。这个筛选是 262 单、R$ 27,106.04。回到订单明细能解释为何整单支付与当前品类金额不同。” |
| 1:05–1:30 | 商品与履约页，展示排名、延迟率和评分分布 | “商品排名只说明观察期销量，不等同库存滞销。缺送达日期的订单保留在销售额里，但不进入延迟率分母；缺评价也不记作零分。” |
| 1:30–1:52 | 客户分析页，展示新老客与 RFM 规则 | “客户用跨订单稳定 ID，7 月有 6,100 位购买客户，其中 58 位在这个月买过至少两单，观察期复购率约 0.95%。频次分布高度集中在一次，所以我用公开的二分 RFM 规则，没有强行五等分。” |
| 1:52–2:18 | 经营报告，展示 7 月与 6 月比较及贡献 | “7 月商品总额比 6 月多 1.39%，但日均金额低 1.88%。这是月份天数差带来的解读风险；我继续按订单量、客单价和品类、地区拆解，而不是直接宣布经营改善。” |
| 2:18–2:42 | 经营报告履约分层，打开案例文档 | “7 月延迟组有 208 单，有评价的 200 单平均 2.755 分；按期组有评价的 5,918 单平均 4.370 分。两组结构和缺失不同，这只是关联，不能说延迟造成评分下降。” |
| 2:42–3:00 | HTML／Markdown 报告、架构图与测试记录 | “报告能保留期间、版本、口径和待核查事项。导入可重复运行，金额经过原始 CSV、数据库和接口交叉核对。下一步真正使用时，还需要活动、库存等数据验证原因；我没有把建议写成已经实现的收益。” |

## 录制前检查

1. 核对页面数据版本与 [案例证据](../reports/case-data/commerce-report-2018-07-01-2018-07-31.json)一致；如有更新，重新核算数字。
2. 本地版启动 API 和前端，四页逐个打开；预先设置浏览器 1440×900 左右，隐藏个人账户、绝对本地路径和终端凭证。
3. 录制中保留项目的“历史数据”标识；展示本地明细时只在本地视频中使用，公开视频不要聚焦订单 ID 或逐单信息。
4. 录制完成后核对 3 分钟内能听清、能读到日期和单位；查看末尾是否显示 Olist 来源及 CC BY-NC-SA 4.0 许可。

现有 [截图索引](SCREENSHOTS.md)提供无需后端也能讲述的顺序；如只用截图合成无声视频，应明确标注“验收截图演示”，不能冒充实时录屏或带声音的讲解。
