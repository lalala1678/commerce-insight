# 客户分析：定义、分布与 RFM 规则

本阶段交付客户分析页面、`GET /api/customers`、客户聚合 SQL、规则与独立核对脚本。
分析使用已导入的真实 Olist 历史订单。结论仅限观察窗口，不代表平台真实全生命周期行为。

## 先看分布

下表由原始 CSV 独立重算并与 MySQL HTTP 接口核对，证据见 [acceptance.json](customers/acceptance.json)。客户以 customer_unique_id 识别，订单按已交付状态和下单日计入。

| 观察窗口 | 购买客户 | 仅买一次 | 窗口内复购客户 | 复购率 | F 的 P75 | M 中位数 / P75（BRL） |
|---|---:|---:|---:|---:|---:|---:|
| 2018-07 | 6,100 | 6,042 | 58 | 0.9508% | 1 | 88.90 / 152.00 |
| 2018-02 至 2018-07 | 38,560 | 37,813 | 747 | 1.9372% | 1 | 89.90 / 151.80 |
| 2017-01 至 2018-07 | 86,960 | 84,351 | 2,609 | 3.0002% | 1 | 89.90 / 155.00 |

三个窗口的频次第 75 百分位都为 1。强行按频次五等分会拆开相同购买行为，或产生重复分位点，因此采用公开的二分规则。
这些窗口长度不同，复购率不能直接用来判定经营改善。没有曝光、注册或全站覆盖信息，也不能把低复购直接归因为产品问题。

## 新老客和复购率

1. 先从截至分析截止日的所有已交付历史中计算每个稳定客户的首次下单日期，不受当前品类或地区筛选影响。
2. 再对当前窗口与维度筛选得到的购买客户分类：首次购买在窗口内为数据内新客；早于窗口为数据内老客。
3. 复购客户是在本窗口、本筛选集合中具有至少 2 笔不同订单的客户。复购率分母是本窗口购买客户总数；无客户时返回 null。

7 月新客 5,949，老客 151，两者合计 6,100。复购客户 58 是另一种划分：新客也可能在一个月买两次，老客本月也可能只买一次。不能用老客数代替复购客户数。
历史抽样存在左截断，“新客”不是注册新客或消费者终身首次购买。

## RFM：rfm-window-v1

RFM 与顶部筛选使用同一个回看窗口。仅纳入窗口内有命中购买的客户；截止日为结束日，包含当天，不使用今天。

| 维度 | 计算 | 分组边界 |
|---|---|---|
| R | 截止日 − 当前窗口命中订单的最近购买日，单位天 | ≤30 / >30 |
| F | 当前窗口命中已交付订单数，按订单 ID 去重 | 1 / ≥2 |
| M | 同一订单范围命中商品项金额之和，不含运费 | <200 BRL / ≥200 BRL |

三项二分形成 8 组，边界包含关系明确，每个客户恰好进入一组。页面直接展示规则标签，不将其命名为“忠诚”“流失”或“高价值”。

阈值的含义：F=2 是实际复购定义；R=30 用于按月观察购买间隔；M=200 BRL 是便于解释的固定探索阈值，略高于这些窗口的金额 P75，并非从收益实验、预测模型或最优分群学到。固定阈值避免每次筛选都把“较高金额”的含义改掉，但不同窗口仍不能直接比较客户价值。修改阈值必须升级规则版本并同步文档、页面和测试。

默认 7 月只有 31 天，因此全部纳入客户的 R≤30。在线静态版新增「2018 年 2–7 月 · 长观察窗 / 全部」预设，观察窗内 38,560 位购买客户中，32,460 位距窗口截止日末次购买 >30 天、6,100 位 ≤30 天。这两个数字覆盖的仍只是窗口内有购买的客户，不能称前者为「所有流失客户」。本地版也可把开始日期设为 2018-02-01；新老客、复购和金额都会随窗口一起重算。本版不增加独立 RFM 回看控件，避免一页混用两套窗口。

只对当前窗口购买者分组意味着：没有购买的历史客户不在 RFM 中，无法据此发现所有潜在流失客户。

## 筛选和粒度

- 客户州使用订单关联的客户记录。一个稳定客户跨州购买，可能在多个州出现；各州客户数不可相加为总客户数。
- 品类仅影响命中商品项金额；一单多商品仍是一次购买。F 与 R 跟随命中订单，首次购买继续使用全维度历史。
- 支付、评价不进入客户金额聚合，避免商品×支付×评价带来重复计数。取消、处理中订单不参与。
- R/F/M 的最小值、中位数、P75、最大值均基于窗口购买客户；P75 用最近秩法，空集合返回 null。
- 所有接口结果包含数据版本与规则版本。不输出客户身份、逐客户购买记录或评价正文。
- 每个响应使用一致性读快照。前端丢弃旧请求；如果与主页面数据版本不一致，提示重新应用筛选，不混合展示。

## 对应文件与复现

- `sql/customers.sql`：客户聚合与不受维度筛选影响的首次购买。
- `backend/customers.py`：规则分组与汇总。
- `frontend/src/Customers.vue`：第三个页面。
- `tests/test_customers.py`：手算样例、跨窗口/品类/地区、未来订单、并列和边界。
- `scripts/verify_customers.py`：标准库 CSV/Decimal 独立重算，再核对实际 HTTP；不复用客户业务计算函数。

启动真实 API 后，在项目根目录执行：

```bash
python -m pytest -q
python -m scripts.verify_customers --api-url http://127.0.0.1:8000
```

核对脚本校验当前 ETL 回执和输入 SHA-256；若更换原始版本，应先重新导入并保存对应回执。完整执行证据见 [本阶段验收](customers/VERIFICATION.md)。
